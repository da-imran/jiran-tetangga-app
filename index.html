Overview

One workspace, one neighbourhood

JiranTetangga began as two separate codebases — a backend API and a resident-facing web app — built and maintained on their own. Both now live in a single pnpm workspace: one version history, one set of conventions, one place to see how the platform actually works.

Two internal libraries hold it together. Shared Zod schemas validate every request and response the same way on both ends, and a shared set of React hooks gives every screen the same documented way of talking to the API.

Architecture

Two legacy repos, one workspace

The backend kept its original CommonJS structure — require() and module.exports — rather than being rewritten just to match a newer convention. It was already a working Express application; rewriting it would have added risk without adding capability.

The frontend arrived already modern: a pnpm-workspace-ready, ESM-based React app built with Vite. Both now sit side by side under one root, sharing two internal libraries instead of duplicating logic between them.

jiran-tetangga-app/
├─ packages/
│  ├─ api-server/         Backend · Express 5 + MongoDB   CommonJS
│  └─ jiran-tetangga/     Frontend · React 19 + Vite      ESM
└─ lib/
   ├─ api-zod/            Shared Zod schemas             ESM
   └─ api-client-react/   Shared React hooks             ESM

Get started

Running locally takes three steps

  1. 1

    Install

    Install Node.js 20 or later and pnpm 9 or later, then install every workspace package with one command.

    pnpm install
  2. 2

    Configure

    Set the Mongo connection string and signing keys for the backend, and point the frontend at the API base URL.

    MONGODB_URI=mongodb://localhost:27017/jiran-tetangga
JWT_KEY=<your-secret>
VITE_API_BASE_URL=http://localhost:8118/jiran-tetangga/v1

    For a complete list of available configuration options, refer to the .env.example files in the project root and packages/api-server/ directories.

  3. 3

    Run

    Launch both applications together with the one-shot script, or run the API and the web app in separate terminals.

    ./run-local.sh

Why I make this project?

The idea came when I was actually looking to buy my first house. I thought of what if we have some sort of website or platform for the community in that area to communicate and do some stuff together. Then this project came out from my head where I try to build a platform that allow the communities or users to look around what's happening in their neighbourhood area. From rumah terbuka, kenduri, missing items and stuff, to booking a dewan, I make an effort to include everything that could be helpful to a community that has a specific platform for its local events.

A bit of details what this project consists of.

1. Backend Engineering (Primary Focus)

The bulk of the codebase is the Express 5 API server at packages/api-server/, deliberately kept as CommonJS to avoid rewriting a working Express app just to follow a newer convention.

  • 13 fully implemented feature modules (adminUsers, bookings, contacts, disruptions, events, facilities, incidents, lostFound, marketplace, parks, reports, shops, userPasswords), each with full CRUD, search, filters, and pagination.
  • A proper data layer in utilities/mongodb.js: connection management, findOne, insertOne, findOneAndUpdate, updateMany, deleteOne, aggregate, and a updateTimeSeries helper for MongoDB time-series collections.
  • Auto-generated OpenAPI docs via swagger-autogen, served at /jiran-tetangga/v1/api-docs.
  • Real bootstrapping in app.js: fail-fast secret loading, Mongo connection, middleware registration, route mounting, Swagger UI, and port binding — each step in a deliberate order.

2. Frontend Development (Some Involvement)

The frontend at packages/jiran-tetangga/ uses React 19 + Vite + TypeScript + Tailwind + Radix UI + TanStack Query + wouter — modern, but not overwhelming.

  • Accessibility menu: high-contrast toggle, font-size stepper, and text-to-speech via the Web Speech API that reads any element marked data-speakable="true"; preferences persist to localStorage.
  • Forms with Zod + react-hook-form (e.g. event-proposal-form.tsx) — same validation on the frontend that the backend uses through the shared @workspace/api-zod library.
  • Shared data layer wrapping TanStack Query, with real fetch logic and loading states for Disruptions, Shops, Parks, and Events.
  • Two shared internal libraries (api-zod, api-client-react) keep both ends honest about the contract.

3. DevOps & CI/CD

  • Dockerfile: Node 20-alpine, pnpm install from lockfile, workspace files copied first for layer caching, and a non-root nodejs user (UID 1001) for runtime.
  • docker-compose.yaml: three services — backend, mongodb (with a real mongosh healthcheck and named volume), and an nginx reverse proxy.
  • Nginx reverse proxy with proper X-Real-IP, X-Forwarded-For, and X-Forwarded-Proto headers — production hardening most demos skip.
  • One-shot launcher (run-local.sh) that picks the Infisical environment based on NODE_ENV and runs both apps in parallel.
  • Structured logging via a custom logger in utilities/logger.js — emits level-routed (critical/error/warn/info/debug) key=value lines to stdout, ready to be collected by any container log driver or downstream pipeline.
  • Workspace-level scripts: pnpm dev, build, typecheck, lint, test — the full monorepo pipeline menu.
  • CI/CD Pipeline (.github/workflows/jiran-tetangga-check.yaml): 2 jobs on every push and PR to main, staging, and development — build compiles the api-server Docker image with Buildx + GitHub Actions layer caching; test spins up MongoDB 8.0 as a service, writes a real .env with INFISICAL_ENV=ci creds, and runs pnpm test (Mocha + Chai + Sinon with sinon-stubbed MongoDB);

4. AI Tools

This project was build with Claude Code — Anthropic's agentic CLI — as the primary development partner, rather than a runtime AI feature inside the app. The integration lives in the .claude/ directory, which holds the configuration and context the agent works against on every session.

  • Scoped autonomy via a permission allowlist (.claude/settings.local.json): What I allow Claude Code to run from such as ls, docker commands, node commands. I avoid to put any destructive command rm -f etc in here otherwise, mess up
  • Claude markdown file: The CLAUDE.md only contains specific instruction for this project, tend to keep it 200 lines max, complete with Claude Skills, commands, rules based on prompt sent.
  • Rules, Plans, Commands: This is the detailed folder that contains what must the AI follow i.e. coding structure, naming conventions, deploy commands and etc, which are injected in the claude.md file. The plans directory was made all documentations on feature development, bug fixes, task etc.

5. Secrets (Infisical)

Full Infisical SDK integration (@infisical/sdk v4.0.4) at utilities/secrets.js:

  • Universal Auth flow (clientId + clientSecret) — the production-safe pattern.
  • Environment-aware: reads INFISICAL_ENV and pulls secrets under path /JiranTetangga.
  • Four named secrets: MONGO_URI, ENCRYPTION_KEY, API_KEY, JWT_KEY.
  • Fail-fast guard: checkSecretObjectNull() returns false if any secret is missing, and app.js calls process.exit(1) — the app won't start with missing secrets.
  • Environment-aware fallback: local/dev uses .env values; other environments use Infisical.

6. AuthN & AuthZ

Both are implemented properly, in separate middleware files.

  • Authentication (AuthN): the login endpoint accepts email + password, AES-decrypts the stored password using ENCRYPTION_KEY from Infisical (crypto-js AES-ECB + PKCS7), and signs a JWT with { id, email } using HS256 and a 15-minute expiry.
  • JWT helpers: verifyToken constrains accepted algorithms to ['HS256'] — preventing algorithm-substitution attacks.
  • Authorization (AuthZ) — layered:
    • Service-level: every request must carry a valid x-api-key matching the Infisical-stored API_KEY.
    • Path-based policy: four paths explicitly excluded from API-key checks (root, versioned base, /forgot-password, /reset-password) — a clean allowlist.
    • Environment-gated: the API-key middleware only runs outside local/dev/development.
    • Admin user management is a first-class module (adminUsers.js) with full CRUD.
What if I don't have Infisical setup for secret management?
If you don't have Infisical configured, you can manually set up environment variables using the provided .env.example files. Simply copy .env.example to .env in the project root and packages/api-server/ directory, then fill in the required values such as MongoDB URI, JWT secret, and other configuration options. The application will read these variables directly from your .env files during development.
How do I run the application in development mode?
To run the application in development mode, first ensure you have completed the installation and configuration steps. Then, simply run ./run-local.sh in your terminal. This script will start both the backend API server and the frontend web application concurrently. You can access the frontend at http://localhost:3000 and the API at http://localhost:8118/jiran-tetangga/v1.
What database does JiranTetangga use and how do I set it up?
JiranTetangga uses MongoDB as its primary database. To set it up locally, you need to have MongoDB installed and running on your machine. The application expects a MongoDB instance running on the default port (27017) with a database named "jiran-tetangga". You can modify the connection string in your environment variables if you need to use a different host, port, or database name.
